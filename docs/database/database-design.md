# StorePilot V2 - Database Design

This is an implementation guide, not a requirement to create every table in one migration. Add tables when their feature is implemented. EF Core migrations remain the schema history.

## 1. Reference and people tables

| Table | Minimum fields | Notes |
|---|---|---|
| Units | Id, Name | Seeded, read-only, unique Name |
| Groups | Id, Name | Seeded, read-only, unique Name |
| PaymentMethods | Id, Code, Name, AffectsCashDrawer | Seeded, read-only; only methods used by the shop |
| People | Id, Name, Phone?, Address? | Shared identity; name required; no assumed unique phone/name |
| Customers | Id, PersonId | PersonId unique within Customers |
| Suppliers | Id, PersonId | PersonId unique within Suppliers |

A person may have both a Customer and Supplier row. Keep role data separate from shared contact details. Do not add CRUD screens for Units, Groups, or PaymentMethods.

## 2. Products and inventory

### Products
Minimum fields:
- Id, Name, Code?, SalePrice, PurchasePrice, MinQuantity, CurrentQuantity
- UnitId, GroupId, IsActive, CreatedAt, Notes?

Keep existing operational fields unless implementation review shows a real reason to remove them. Product Code is unique when supplied. Review whether Name should be unique against the actual catalog before changing its existing constraint. Referenced products remain available for history; inactive products cannot be used in new documents.

### StockTransactions
- Id, ProductId, TransactionDate, QuantityChange, MovementType, Notes?
- Record opening stock, purchase, purchase return, sale, sales return, and approved adjustment.
- Generated by business workflows; no unrestricted CRUD.
- Update CurrentQuantity in the same transaction as the movement.
- Prevent negative stock.

An opening stock/adjustment operation is needed even before purchasing is complete. Purchase invoices later become the normal source of stock increases.

## 3. Purchase and supplier tables

### PurchaseInvoices
- Id, InvoiceNumber, InvoiceDate, SupplierId?, PurchaseType, TotalAmount, Status, Notes?
- SupplierId is required for Credit purchases. It may be null for a fully paid cash purchase if the shop does not need supplier details.
- Immediate purchases are fully paid in the initial workflow; Credit purchases create supplier debt.

### PurchaseInvoiceItems
- Id, PurchaseInvoiceId, ProductId, ProductNameSnapshot, UnitNameSnapshot, Quantity, UnitCost, LineTotal
- Preserve snapshots and validate positive quantity/cost.

### PurchaseReturns and PurchaseReturnItems
- Return header references the original PurchaseInvoice.
- Return items reference original PurchaseInvoiceItems.
- Returned quantity cannot exceed the remaining quantity.
- A return decreases stock and reduces supplier payable.
- If the return exceeds the current supplier payable, keep the difference as supplier credit; supplier cash refunds are deferred.

### SupplierAccountEntries
- Id, SupplierId, EntryDate, DebitAmount, CreditAmount, Description, and a source relationship.
- Credit increases what the shop owes the supplier; Debit reduces it.
- Credit purchase creates Credit; purchase return and later supplier payment create Debit.
- A negative payable means supplier credit is available to offset later purchases.
- Entries are generated by operations, not manually edited.

SupplierPayments is intentionally deferred to a later feature. Do not block purchase invoice and purchase return implementation on it.

## 4. Customer and sales tables

### SaleInvoices
- Id, InvoiceNumber, InvoiceDate, CustomerId?, SaleType, TotalAmount, Status, Notes?
- SaleType is Immediate or Credit and is preserved as the original sale condition.
- Credit requires CustomerId. Immediate may be anonymous or registered.
- Anonymous sales must be fully paid.

### SaleInvoiceItems
- Id, SaleInvoiceId, ProductId, ProductNameSnapshot, UnitNameSnapshot, Quantity, UnitPrice, LineTotal
- Preserve the original values needed to calculate later returns.

### SaleInvoicePayments
Records the full payment made at the time of an Immediate sale in the first workflow. It references the payment method. For a registered customer, the sale debit and its immediate payment credit may both appear in the customer ledger. Anonymous sales have no customer ledger.

### CustomerReceipts
- Id, CustomerId, ReceiptDate, Amount, PaymentMethodId, Notes?
- Independent of SaleInvoiceId; supports partial debt collection.
- Cannot exceed the current customer debt.
- Creates a customer ledger credit. Creates a cash movement only when the method affects the cash drawer.

### CustomerAccountEntries
- Id, CustomerId, EntryDate, DebitAmount, CreditAmount, Description, and source relationship.
- Debit increases customer debt; Credit reduces it.
- Sale on credit creates Debit; immediate payment and later receipt create Credit; return value reduces debt through Credit.
- If return value exceeds debt, record the excess cash refund as a balancing Debit and a cash outflow.
- Balance = Sum(DebitAmount) - Sum(CreditAmount).
- Do not expose direct CRUD.

### CustomerOpeningBalances
Add only if the shop needs to migrate existing debts. Each opening balance must create its ledger entry.

## 5. Sales returns and refunds

### SaleReturns and SaleReturnItems
- SaleReturns references the original SaleInvoice.
- Each item references the original SaleInvoiceItem.
- Customer identity is inherited from the invoice; anonymous sales remain anonymous.
- Record return date, reason, quantities, and calculated return value.
- Increase stock and reduce customer debt atomically.

### Refund
For the first workflow, record the actual refund amount and payment method on the return (or in a one-to-one child table if the implementation needs it). A separate multi-refund table is not needed unless partial/multiple refunds become a real requirement. Cash refunds generate a CashTransactions outflow.

## 6. Cash and payment methods

### CashTransactions
- Id, TransactionDate, Amount, Direction, Description, and source relationship.
- Represents physical cash movement only.
- Generated from cash sales, cash purchases, actual refunds, and later cash debt payments.
- No generic CRUD.

PaymentMethods is a read-only seeded lookup. AffectsCashDrawer distinguishes physical cash from electronic/non-cash methods.

## 7. Constraints and implementation notes

- Use restrictive foreign keys for referenced lookup values and historical documents.
- Add unique indexes for invoice numbers and product codes; add indexes for foreign keys and common date/customer/supplier queries.
- Add check constraints for positive quantities and amounts, valid movement direction/type, and mutually valid document fields.
- A posted document must not be deleted or silently edited.
- Keep stock, customer/supplier ledger, and cash changes in the same database transaction as the source document.
- Avoid a polymorphic SourceType + SourceId as the only relationship where it would remove foreign-key integrity. Use explicit nullable source foreign keys or a simpler source-specific relationship when implementing the ledger.
- Do not create all future tables now. Build and migrate one feature at a time.
